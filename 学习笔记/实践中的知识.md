- 工具的“诊断输出”有层级：Error > Warning > Note。Warning 不等于“坏了”，只等于“可以更好”。 Homebrew 的 brew doctor 把“有更新可用”和“系统配置异常”都归在 Warning 里，但它们对“能不能正常装软件”的影响完全不同。**学会区分警告的严重程度**，比盲目追求“全绿”更能节省冲刺项目里的时间。
- “冲突”往往不是工具本身不兼容，而是默认行为的叠加造成了优先级混乱。 Anaconda 默认激活 base、把自己排在 PATH 最前面，这是为了方便“纯 Python 用户”；但当你同时是 Homebrew 用户时，这个“方便”就变成了“干扰”。解决这类问题的通用思路是：不要卸载工具，而是调整它们的默认行为，让每个工具只在被显式调用时生效。conda config --set auto_activate_base false 这一行命令，比卸载重装更能保护你的环境——因为它保留了隔离能力，只是把“什么时候隔离”的控制权还给了你。
- 安装命令其实因为文件被另一个 brew 进程锁住而中断了，所以 Node 24 并没有装成功。至于用哪个：你的项目用现有的 Node 26 就够了，不需要执着于安装 24。“安装失败”和“版本不对”是两件独立的事。 你这次的困惑，本质上是把 brew 安装中断（锁冲突） 和 当前生效的 Node 版本 混在了一起。在命令行里，一个命令失败不等于环境被破坏；which node 和 node --version 永远告诉你此刻真正在用的版本。学会分开看“操作结果”和“环境状态”，能帮你避免大量“我明明装了 A，为什么显示 B”的无效排查。
- 一句话总结：工具探针（doctor）永远先于业务代码，装 OpenCLI 现在就做；建项目那 5 分钟什么时候插进来都行。跑完 opencli doctor 和 opencli list 后把输出发我，我们直接进字段确认环节。

- “命令不存在”和“解释器不存在”是两件完全不同的事。 遇到 command not found，第一反应不应该是“我是不是没装 Python”，而是先问“这个命令到底叫什么名字”——用 which python3、python3 --version 确认解释器活着，问题就降级成了“只是命令名对不上”。先验证实体是否存在，再处理名字映射，这个思维习惯能帮你跳过大量无效的“重装环境”操作。
- “有新版本”提示需要分级看待：例行功能更新可以忽略，安全补丁应当尽快执行。 pip 的 [notice] 本身不区分这两种情况，但你可以通过查看 release notes 或搜索版本号 + “security” 来判断。这次 26.2.2 的核心变更就是更新 certifi 证书包，属于安全类，所以值得花 30 秒升级；如果是一个纯粹的性能优化版本，在冲刺项目里跳过它完全合理。学会区分“可忽略的版本提示”和“必须处理的安全更新”，比盲目执行所有升级提示更能保护你的时间和环境。**这里要在venv环境内执行升级命令，而且是用 python -m pip 而不是直接 pip**【为什么？】
- 工具不仅认“内容”，还认“绝对路径”。 为什么改了文件夹名字，venv 就得重装？因为 venv 激活的本质，是修改环境变量 PATH，指向一个被写死在 pyvenv.cfg 里的绝对路径。文件夹一改名，它指的地方就空了。同理，以后你配置 Hermes 或 OpenCLI 时，只要牵涉到“指定路径”（比如配置数据库路径、日志路径），请第一时间确认：路径里绝对不能有中文和空格。这能为你省下无数的 Debug 时间。
- Git 设计精妙的地方在于它的“相对路径追踪”与“状态保存”机制。 你在旧目录里执行的 git init 和 commit，实际上是在那个文件夹里创建了一个 .git 的快照数据库。当你把整个文件夹（包含 .git）移动到新路径时，Git 仍然认为所有的文件都在原地，因为它记录的永远是与 .git 文件夹的相对距离。这就是为什么“系统级工具（全局安装）”和“项目级配置（被 Git 追踪）”在面对目录改名时，永远不需要推倒重来，你只需要验证它们“有没有跟着走”就行了。
